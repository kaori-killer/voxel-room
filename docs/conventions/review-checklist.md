# 코드 검수 8축 체크리스트

리뷰할 때 8개 축을 모두 훑는다. 해당 없는 축도 **생략하지 말고 "해당 없음"** 으로 적는다.
작은 변경도 같은 형식을 지켜 누락을 막는다.

이 프로젝트의 컨벤션 소스 오브 트루스는 **`docs/`** 다 (특히 `code.md`, `naming.md`, `commit.md`).
기계가 강제하는 것은 `eslint.config.mjs`, `tsconfig.json`, `commitlint.config.mjs`.

## 적용 강도

| 변경 규모 | 적용 축 |
| --- | --- |
| 신규 페이지/컴포넌트 | 8축 전부 |
| 기존 UI 컴포넌트 수정 | 8축 전부 |
| 비-UI 로직(hook/유틸/서비스) | 2·3·4 생략 가능, 나머지 적용 |
| 오타/주석/1~2줄 | 1·6만 |

## 1. 컨벤션

- **소스 오브 트루스를 먼저 열고 대조한다.** 기억·추론으로 판단하지 않는다.
- 네이밍 일관성: 파일·컴포넌트·함수·변수·타입
- 타입 규칙: 금지 타입(`any`), `type` vs `interface`, 접미사
- 폴더 구조·모듈 배치, 공개 API 경계
- **새 패턴 도입 전에 같은 일 하는 기존 코드를 grep 해서 맞춘다.** 혼자 새 방식을 만들지 않는다
- 보고: "규칙 X 준수 ✅ / 위반 ⚠️ (파일:라인)" — 어느 규칙 위반인지까지

## 2. 시맨틱 태그 / 구조

- `main`/`header`/`footer`/`nav`/`section`/`article`/`form`/`dl` 을 적절히
- 의미 없는 `div` 래퍼 남발 여부
- 헤딩 위계(`h1`→`h2`→`h3`, 건너뛰기 금지)
- `main` 은 페이지당 1개, 중첩 없음
- 목록은 `ul`/`ol`/`dl`, 표는 `table` + `th`/`caption`

## 3. 키보드 동작

- Tab 순서가 시각적 흐름과 같은지
- 포커스 가시성(`:focus-visible`)
- 모달·드롭다운·팝오버 `Esc` 닫기
- 폼 `Enter` 제출 (submit 버튼 존재)
- 클릭 요소가 `button`/`a` 인지 (`div + onClick` 지양)
- `Space`/`Enter` 로 활성화되는지

## 4. 접근성

- 이미지 `alt` (장식은 빈 alt)
- 텍스트 없는 컨트롤에 `aria-label`
- label ↔ input 연결
- 색 대비 WCAG AA (본문 4.5:1, 큰 글자 3:1) — 시안이 위배하면 먼저 알린다
- `autoFocus` 남용 자제
- 접근성 라벨과 `placeholder` 는 역할이 다르다 → 같은 문구 금지
- 상태를 색으로만 전달하지 않기

## 5. 사용자 수정 차이

사람이 생성 코드를 직접 다듬었을 때만.

```
## 발견한 차이 (생성본 vs 사용자)
1. <항목> — <의도 추정 한 줄>

## 룰화 제안
- <일반 룰인지> / <어디에 어떤 형태로 기록>

## 문제점 (있으면)
- ⚠️ <문법 오류/버그/미사용 import> + 수정 권장 형태
```

## 6. 코드 품질

- **불필요한 주석 금지** — 동작 설명 ❌, *왜* 그렇게 했는지·외부 계약만 예외
- **미니멀 prop/인자** — 무시되는 기본값, 불필요한 메모이제이션, override 되어 사라지는 스프레드 제거
- ⚠️ **디버그 잔재** — `console.*`/`debugger` 등: 변경 파일 grep, 남으면 무조건 보고 + 제거(위치 + 줄 내용). 제거 후 린트·타입체크 재확인
- `TODO`/`FIXME` 잔존 → 제거 또는 이슈화
- 미사용 import·변수·죽은 코드
- 매직 넘버·문자열 상수화, 중복 로직 추출
- 에러 처리·엣지 케이스(빈 값/로딩/실패) 누락 여부

## 7. 정적 검증

- 신규·수정 파일이면 린터 + 타입체커를 **직접 실행** (통과 추정 금지)
- 관련 테스트 실행, 실패 시 결과 첨부 + 수정 제안
- 포매터 적용 상태 확인

이 프로젝트에서는 `npm run verify` (lint + typecheck + unit/integration) 한 줄.

## 8. 설계 (SOLID)

- **S 단일책임** — 한 모듈이 다루는 책임 개수. 섞였으면 분리 신호
- **O 개방폐쇄** — 새 동작을 기존 코드 수정 없이 넣을 수 있는지 (if/else 가 계속 늘면 신호)
- **L 리스코프** — 좁힌/파생 타입이 원본과 호환되는지
- **I 인터페이스분리** — 노출한 API 중 소비자가 실제 쓰는 비율. 절반 이상 미사용이면 분리 신호
- **D 의존성역전** — 상위 모듈이 구체 구현에 직접 의존하는지 → 추상 계층으로 격리

> ⚠️ 위반 = 무조건 수정 아님. **명백한 위반 + 향후 변경에 발목 잡힐 가능성** 이 있을 때만 짚는다.

## 표준 보고 형식

```
## 변경 요약 — 파일별 한 줄
## 1. 컨벤션         — ✅ / ⚠️ 항목별
## 2. 시맨틱/구조     — ✅ / ⚠️
## 3. 키보드          — ✅ / ⚠️
## 4. 접근성          — ✅ / ⚠️
## 5. 사용자 수정 차이 — (해당 시 3섹션)
## 6. 코드 품질       — ✅ / ⚠️
## 7. 정적 검증       — 결과
## 8. 설계(SOLID)     — S/O/L/I/D 항목별 ✅/⚠️/해당 없음
## 종합              — 머지 가능/수정 필요 + 우선순위
```

이슈가 없는 섹션도 **"✅ 이슈 없음"** 한 줄로 남긴다.

## 안티 패턴

- "확인 완료" 한 줄로 끝내기
- 사람이 직접 수정했는데 차이 보고 없이 넘어가기
- 린트·타입체크 안 돌리고 "통과 추정" 보고
- "UI 아니라서" 시맨틱·a11y 자동 생략
- 컨벤션 위반을 "참고" 정도로 약하게 보고
- SOLID 무리한 적용으로 over-engineering 권장
